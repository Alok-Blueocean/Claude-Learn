# CCAR-P: Advanced Architecture Scenario Q&A

12 original scenario Q&As, written for this study kit, going beyond anything in the official exam guide (which, as `official_scenarios.md` explains, has no named scenarios at all). These target the production-scale judgment calls a Claude Certified Architect – Professional candidate is expected to make: multi-region data residency, cost governance across many teams, evaluation pipelines for agentic systems, model-generation migration, and multi-agent supervision — the kind of depth-and-scale material that distinguishes this exam from CCAR-F.

---

**Situation:** A financial-services company operates in the EU, the US, and Singapore, and wants one Claude-based document-processing system serving all three regions. EU regulators require that EU customer data never leave EU jurisdiction; Singapore's regulator has a similar but not identical requirement. The team's instinct is to build one global deployment with a single API endpoint and route by request origin. What's wrong with that instinct, and what should the architecture look like instead?

Model answer: A single global deployment with request-time routing addresses network-path residency but not data-at-rest and data-in-processing residency — logs, cached prompts, retrieved documents, and any stored conversation history for an EU customer's request must also stay in EU jurisdiction, not just the model call itself, and a single shared logging/storage layer behind one global endpoint will not satisfy that. The correct architecture is regional deployment isolation: separate infrastructure stacks per jurisdiction (EU, US, Singapore), each with its own storage, logging, retrieval index, and prompt-cache scope, so that an EU request's data never transits or persists outside EU infrastructure at any layer, not just the inference call. Shared components (a common system-prompt template, a common eval harness, common code) can and should be shared across regions — what cannot be shared is the data plane. Because Singapore's requirements differ subtly from the EU's (e.g., different definitions of "sensitive" categories or different cross-border transfer exceptions), don't assume one regional isolation policy fits both; each jurisdiction needs its own compliance review of the same architecture pattern, not a copy-paste of the EU config. Routing logic (which regional stack handles a given request) should be determined by the data's jurisdiction of origin, decided as early as possible in the request path — ideally before any document content is read into a shared component at all — and that routing decision itself should be logged and auditable, since "we correctly routed this EU customer's data to the EU stack" needs to be demonstrable to a regulator, not just true in practice.

**Situation:** Forty product teams inside one company all consume Claude through a single shared enterprise API account. Finance reports monthly spend has tripled in six months with no corresponding growth in usage that anyone can explain, and nobody can say which team is responsible for how much of it. What governance model fixes this, and what would you actually implement first?

Model answer: The root problem is a shared credential with no cost attribution — from a pure spend perspective this is the same "shared, over-broad configuration" failure the exam tests at the security layer (Domain 3), just applied to cost instead of access. Fix it in three moves, in order of speed to value. First, attribute: issue per-team API keys or workspace/project scoping (whatever the platform's isolation primitive is) so every request is tagged to an owning team, and stand up a shared cost dashboard broken out by team, model, and request volume — you cannot govern what you can't attribute, and this alone often surfaces the actual outliers within days. Second, cap: set a soft budget alert and a hard budget ceiling per team, informed by their attributed baseline once you have a few weeks of attributed data, so one team's runaway agentic loop or un-cached high-volume workflow can't silently balloon the shared bill before anyone notices. Third, standardize: publish a small number of platform-blessed patterns (a model-cascade router for high-volume classification, a shared prompt-caching convention, a shared multi-model endpoint or equivalent for low-traffic use cases) so teams aren't independently reinventing — and mis-costing — the same optimization decisions Domain 2 and Domain 4 cover. The fastest single lever, before any of the above is fully built out, is usually finding the one or two teams running an unbounded agentic loop or un-cached high-frequency call pattern — that's disproportionately often the actual source of a spend tripling, and attribution is what lets you find it instead of guessing.

**Situation:** A team is building an evaluation pipeline for a multi-agent customer-service system (orchestrator + 4 worker agents) that will run at 200,000 requests/day. Their current evaluation approach — a 150-example golden set re-run manually before each release — worked fine for a single-call system but clearly won't scale to catch issues in a system this complex and this high-volume. What does an evaluation pipeline built for this scale actually look like?

Model answer: Scale changes both what you evaluate and how you evaluate it. What changes: with a multi-agent system, you need evaluation at more than one level — end-to-end task success (did the customer's issue actually get resolved correctly), and per-hop correctness (did the orchestrator decompose correctly, did each worker's output meet its own local quality bar), because an end-to-end score alone won't tell you which of five hops is degrading when it slips. How it changes: a 150-example manual golden set can't run before every release at this request volume and complexity, so the pipeline needs continuous, automated layers — a fast golden-set regression check (still valuable, but now gated in CI, not manually run), LLM-as-judge scoring applied to a statistically meaningful sample of live traffic continuously (not just pre-release), and a human-review sample specifically to keep the LLM-judge itself honest over time, since a judge whose calibration silently drifts is worse than no automated judge at this volume. Layer in adversarial/red-team test generation specifically against the tool-permission surface (can a worker agent be manipulated into calling a tool outside its intended scope), since a multi-agent system has more attack surface than a single call. Finally, build alerting on rate-of-change in the aggregate metrics (task-success rate, per-hop failure rate, cost per resolved case, safety-flag rate) rather than expecting a human to notice a slow degradation by eyeballing a dashboard — at 200,000 requests/day, a 3% degradation in task success is a large absolute number of failed customer interactions before anyone would catch it by inspection alone.

**Situation:** A company has been running a production system on one Claude model generation for 18 months, with a system prompt and evaluation suite carefully tuned to that model's specific behavior. A newer model generation is available with better benchmarks. Leadership wants to migrate "as soon as possible." What's the risk in doing that quickly, and what's the right migration process?

Model answer: The risk is exactly the model-mismatch failure mode this blueprint names directly: a system prompt tuned to one model's specific instruction-following quirks and output tendencies is not guaranteed to transfer cleanly to a different model generation, even a strictly more capable one — better benchmark scores on general tasks say nothing about whether this specific prompt, with its specific edge-case handling, still produces the same behavior. "As soon as possible" without validation risks a silent regression that the team won't notice until user complaints arrive, precisely the trap Domain 4's diagnostic material warns about (assuming a problem is something else when it's actually a model-version mismatch — here, inverted: assuming a migration is safe because the model is "better," when better-on-average doesn't mean better-on-this-prompt). The right process: treat the new model generation as a candidate exactly like any other change under Domain 4's A/B testing discipline — run the full existing evaluation suite (golden set, LLM-as-judge, safety/adversarial set) against the new model with the *current* system prompt unmodified first, to isolate whether the model transition alone causes regressions before any prompt retuning muddies the comparison. Where regressions appear, retune the prompt specifically for the new model's behavior (not just reuse the old one), and re-run the full suite again. Only then canary a small percentage of live traffic, compare the full metric set against the incumbent over a meaningful sample, and ramp gradually — the exact same discipline as any other prompt/model change, not a special exception just because the new model is "newer and better." Keep the old model/prompt combination easily reachable (a fast rollback path) until the new combination has proven itself in production, not just in offline evaluation.

**Situation:** A team is designing a multi-agent research-assistant system with one supervisor agent and eight specialized sub-agents (web research, code execution, data analysis, citation-checking, and four domain-specific research agents). Early testing shows the system produces excellent results but costs 40x more per request than a single-call baseline and takes 25 seconds end-to-end. The team's first instinct is to negotiate a higher latency SLA with the business. What should you push back on, and what should you actually investigate first?

Model answer: Push back on treating a higher SLA as the first move — that accepts the current architecture's cost/latency profile as fixed and asks the business to absorb it, when the more likely issue is that the decomposition itself is over-engineered relative to the task. Before renegotiating anything, investigate whether every one of the eight sub-agents earns its hop: for a given real request distribution, how often does the supervisor actually need all eight, versus how often two or three would suffice for the specific question asked? If most real requests only need a subset, the fix is a smarter supervisor that dispatches only the sub-agents relevant to a given request (dynamic fan-out) rather than always invoking all eight (static fan-out) — this alone can cut typical-case cost and latency dramatically without touching quality on the requests that genuinely need full decomposition. Second, check whether independent sub-agents (e.g., citation-checking and code execution, if they don't depend on each other's output) are running sequentially when they could run in parallel — serialized independent hops is one of the most common unforced latency costs in a supervisor design. Third, apply prompt caching aggressively across sub-agents that share a static system-prompt/tooling prefix, since eight agents each re-paying the same static prefix cost compounds fast. Only after those three levers are exhausted does it become reasonable to ask whether the *remaining* cost/latency is a genuine, justified trade-off for the task's value (e.g., a comprehensive research report that would otherwise take a human analyst hours) — and if so, negotiate the SLA from that informed position, not as a first resort.

**Situation:** A regulated healthcare system's Claude-based clinical-documentation assistant has been running smoothly for a year. A new state law now requires that any AI-generated clinical note include an explicit, human-auditable record of what source data influenced the AI's suggestion, for any note a clinician did not fully rewrite. The current system logs only the final generated note and a timestamp. What architectural gap does this expose, and how do you close it without redesigning the whole system?

Model answer: The gap is a transparency/auditability gap that was survivable under the old requirements but is now a compliance failure: logging only the final output with no linkage back to the specific inputs (which patient record fields, which retrieved reference material, which prior notes) that shaped it means there is no way to reconstruct "why did the AI suggest this" after the fact — exactly the kind of transparency failure this blueprint's governance domain flags as a risk when logging isn't designed to support explainability, not just debugging. Closing it doesn't require a full redesign; it requires extending the existing trace/logging layer (which, if the system already has request-level tracing for operational debugging, is a natural extension point) to capture and persist, per generated note: the specific input fields/documents read, any retrieved reference content used, the model/prompt version, and — for notes not fully rewritten by the clinician — a flag distinguishing "AI-suggested, clinician-reviewed-and-kept" from "clinician-authored" so the audit record correctly reflects provenance. This should be added as a structured, queryable record (not just a longer free-text log line), since the whole point is that an auditor or regulator needs to query it later, not just that it exists somewhere. Treat this as a new logging/data-model requirement layered onto the existing pipeline's trace point, and validate it against the specific statutory language (what exactly counts as "influenced," what counts as clinician full-rewrite) with legal/compliance stakeholders before considering it closed — a technically complete audit trail that doesn't match the law's actual definitions is still a compliance gap.

**Situation:** Your organization wants to let 15 internal teams each build their own Claude-based tools, but a recent incident showed two teams had each built customer-facing agents with destructive tools (data deletion, account changes) with no consistent review process — one was caught only because a customer complained. Leadership asks for a governance process that doesn't slow every team down with a heavyweight review for every single change. What do you propose?

Model answer: Use a risk-tiered review process rather than a uniform one — this is the same decomposition-by-risk-tier principle from solution design, applied to governance process itself. Tier 1 (read-only tools, internal-only audiences, no PII/PHI): self-service, no formal review required, but must still go through a lightweight automated checklist (tool-permission scope declared, logging enabled) enforced by CI/deployment tooling rather than a human reviewer, so it doesn't bottleneck fast-moving teams. Tier 2 (customer-facing but non-destructive: drafting, informational responses, non-financial recommendations): a lightweight peer/platform-team review focused specifically on tool scope and guardrail layering (Domain 5's layered-guardrail model) before launch, plus mandatory inclusion in the shared observability/eval dashboard. Tier 3 (any destructive, financial, or irreversible tool capability, or any regulated-data handling): mandatory structured review by a central AI governance function before launch, explicitly checking least-privilege tool configuration, HITL gating on the destructive actions specifically, and compliance sign-off where relevant data categories are involved — this is exactly the tier the incident fell into and should never have skipped review. Critically, the tiering criterion itself (does this tool touch destructive/financial/regulated capability) should be a mandatory, automatically-checked declaration at build time — a required manifest field, not a judgment call left to each team — so that a team can't accidentally (or otherwise) self-classify a Tier 3 system as Tier 1 to avoid review, which is effectively what happened in the incident described.

**Situation:** A retail company's Claude-based product-recommendation agent uses RAG over a product catalog that gets re-indexed nightly. During a Black Friday-scale traffic spike, the on-call engineer notices retrieval latency has tripled compared to a normal Tuesday, though the underlying catalog size hasn't changed. What's the most likely cause given a scale-driven (not content-driven) trigger, and how do you validate it?

Model answer: Since the trigger is traffic volume, not catalog content or size, the most likely cause is retrieval-infrastructure saturation under load — the vector index or retrieval service itself hitting a throughput ceiling (connection pool exhaustion, insufficient replica capacity, or a shared retrieval service being starved by concurrent load from other systems), not a retrieval-quality problem the way a document refresh would be (that's a different, content-driven diagnostic path). Validate by checking retrieval-layer metrics specifically, isolated from the rest of the pipeline: queries-per-second against the retrieval service's known capacity ceiling, connection pool/queue depth at the retrieval layer, and whether retrieval latency alone (not end-to-end request latency) has degraded — if retrieval-specific latency tracks the traffic curve while catalog freshness and index correctness are unchanged, that confirms a capacity problem rather than a data problem. The fix is a scaling response, not a content or model fix: pre-scale retrieval service replicas ahead of a known-large traffic event (Black Friday is predictable, unlike an organic spike), add request queuing/backpressure so the system degrades gracefully (e.g., serving slightly staler cached recommendations under extreme load) rather than failing outright, and set a specific SLA-driven autoscaling trigger on the retrieval layer's own utilization metric, not just on the application layer's request count, since the two can diverge under load in exactly the way this scenario describes.

**Situation:** A B2B SaaS company sells the same Claude-powered support-agent product to customers ranging from a 5-person startup to a 5,000-employee enterprise. The enterprise customers are demanding SSO-integrated authorization so the agent only ever accesses data scoped to the specific end-user's role within their own company, while the smaller customers just want it to work with minimal setup. How do you architect authorization so both segments are served well without maintaining two separate systems?

Model answer: Design one authorization model with a pluggable identity/scoping layer, rather than genuinely separate systems for the two segments. The core principle — the agent's data access must be scoped to the specific requesting end-user's actual permissions, not to a single tenant-wide credential — has to hold for every customer regardless of size; what differs is how that user-level identity and role information is sourced. For enterprise customers, integrate with their SSO/identity provider (SAML/OIDC) so the agent's tool calls carry the authenticated end-user's actual role/permission claims, and enforce authorization checks against those claims at the tool-execution boundary, not just at login. For smaller customers with no SSO investment, provide a simpler default (e.g., a lightweight built-in role model — admin/member — configured directly in the product) that still enforces the same per-user scoping principle, just sourced from a simpler identity store instead of an external IdP. The architectural discipline that makes this maintainable as one system rather than two: keep the authorization *enforcement* logic (what a given role is allowed to access, checked at tool-call time) completely decoupled from the authorization *sourcing* logic (where role/identity information comes from — SSO claims vs. the built-in store), so adding SSO support is an additional identity-source plugin, not a fork of the authorization model itself. This also means a security or compliance review of the enforcement logic covers both segments at once, rather than needing two separate audits.

**Situation:** A team maintains a Claude-based system where the system prompt has been edited over a year by six different engineers, none of whom left comments explaining specific instruction additions. The team wants to remove what looks like a redundant instruction but is afraid it was added for a reason nobody remembers. How do you approach this safely, and what does it say about how the prompt should have been managed from the start?

Model answer: Treat the system prompt exactly like production code with unclear provenance: don't remove anything based on a hunch, and don't leave it either — instrument first. Before touching the instruction, add the eval suite's ability to specifically test what happens with and without it: run the current golden set, adversarial set, and a targeted set of edge cases resembling whatever the instruction plausibly addresses, once with the instruction present (baseline) and once with it removed (candidate), and compare the full metric set (Domain 4's accuracy/latency/cost/safety), not just the golden set — if the instruction was added for a rare edge case, a golden-set-only comparison could easily miss the regression. If no measurable difference appears across a reasonably thorough eval pass, canary the change on live traffic (Domain 4's A/B discipline) before fully removing it, since some edge cases only show up in live traffic distribution, not any offline eval set. What this scenario really indicates is a process gap that should be fixed going forward regardless of this specific instruction's fate: every system-prompt change should be committed with a required rationale (what failure or requirement this addresses, ideally linked to a specific eval case or incident), version-controlled with diffs reviewable like code, and the eval suite should gain a regression test for any instruction added specifically to fix a production issue — so future "why is this here" archaeology isn't necessary, and future removals can be validated against the exact case that originally motivated the addition.

**Situation:** An architecture review board is comparing two proposals for a document-summarization feature expected to run at high volume: Proposal A fine-tunes a smaller model on the company's document types; Proposal B uses RAG with a larger base model and no fine-tuning. Both proposals claim to be "the right choice." How do you evaluate this without just picking a default?

Model answer: This is a trade-off to evaluate against the specific task and constraints, not a contest with one universally correct answer. Fine-tuning (Proposal A) is well-suited when the task requires the model to reliably reproduce a specific style, format, or domain-specific behavior pattern across every request, and when that behavior is stable over time — the cost is an upfront training investment, an ongoing retraining burden whenever the underlying document types or desired behavior shift, and reduced flexibility for one-off changes (a new formatting requirement means a retrain, not a prompt edit). RAG with a larger base model (Proposal B) is well-suited when the task requires access to a large or frequently-changing body of source content, when new document types or edge cases will keep appearing after launch, and when quick iteration (prompt or retrieval changes deployable immediately, no retraining cycle) matters — the cost is the larger base model's higher per-request price and reliance on retrieval quality (Domain 3's chunking/indexing concerns) rather than baked-in knowledge. The deciding questions for the review board: how often do the underlying documents/desired behavior actually change (favors RAG if frequently), is the required behavior narrow and stable enough to be worth a training investment (favors fine-tuning if yes), and what does the cost model look like at the actual expected volume (a smaller fine-tuned model can be cheaper per request at very high volume, which may offset the upfront training cost if volume is large and stable enough). Note the two aren't mutually exclusive either — some production systems fine-tune a smaller model for stable core behavior *and* pair it with retrieval for the frequently-changing content it needs to reference, and the review board should ask whether that hybrid was even considered before treating this as a binary choice.
